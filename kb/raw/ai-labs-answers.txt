what we processed, and the suggestion deduplication key makes a replay after a crash

Topic 2: What does the orchestrator need to read from Veda?
Question: What is the minimum context the orchestrator needs for the MVP, and how
does the context integration work (schemas, authentication, errors, retries, idempotency,
observability)?
Answer: One context endpoint per project, plus the methodology-version endpoint,
covers the MVP. The minimum context:
1. Project: tenant, project ID, name, status and health, key dates (start, go-live,
milestones, training).
2. Team: for each member, user ID, name, project role or roles, access level, owner flag,
and assignment metadata (date added; allocation if available). We use this to choose
who receives a suggestion (topic 4).
3. Methodology: the pinned version, the current stage, the stage's activities, the policies
that apply (stage-linked and standalone) as {policy_id, revision} or resolved
content, and a separate instructions field (open question #7). Instructions are client-
written, so we treat them as untrusted input, never as commands to our system.
4. Suggestion history: what we already sent on the project and where each one stands,
so we don't repeat ourselves.
5. Signals: whether Slack or Teams is connected. Certinia data (opportunity stage, RAID)
keeps coming through Integration Sync's existing Certinia context endpoint.
How the integration works:
Schemas: request and response shapes published as JSON Schema, with a version
(topic 5); we validate against them in CI.
Authentication: as in Technical details.
Errors: {detail, code, meta, request_id} , with stable error codes.
Retries: reads are idempotent; we retry timeouts and 5xx responses with backoff,
never 4xx.
Caching: a 60-second cache per project, cleared by that project's events, is fine for us.
Observability: we send X-Request-Id on every call and both sides log it.

Answer: The orchestrator picks the users; the suggestion names them and the role it

1. Veda provides the team: project ID, user ID, role or roles and assignment metadata for

Topic 5: Shared values and versioning
Question: Which shared lists and canonical values do both teams use (event, trigger,
activity and suggestion types, status values and other integration fields), and how are
events, methodology schemas, activity types and APIs versioned so changes don't break
the integration?
Answer: One catalog in Veda, read through the catalog endpoint, is the source for every
shared value:
Keys are lowercase and never change once used; labels are display-only.
Events and triggers are named <domain>.<entity>.<event> ; reasons and status
values use snake_case.
The catalog includes status values (suggestion, outcome, methodology, project health),
not just types.
An unknown key is rejected with an error, never guessed.

Each event type, the methodology schema, the activity-type list, the catalog and each
API carries a version ( schema_version in payloads; a version in the API path or

Adding a value or an optional field is a minor change: readers ignore what they don't
know. Our contracts already read this way.
Renaming or removing a key, or making a field required, is a new major version. Both

changes this alone.
The catalog has a version or hash, so we notice changes.
Time-based triggers: if a December use case needs one, Veda's scheduler adds one
scheduled event per project to the feed (topic 1), and we evaluate date rules against the
project's context. Moonnox owns that clock.

Policies, activities and autonomy
Question: How do a policy's natural-language trigger and an explicit configured trigger
coexist? How are activity descriptions and explicit agent or action assignments read?
How is autonomy configured, and what's the difference between a suggestion and an
autonomous action?
Answer:
Explicit and natural-language triggers. The explicit trigger decides when a policy is
looked at; the text decides whether it applies and what to suggest. A policy with only
text is checked against the December triggers, not every event. If the text contradicts
the configured trigger, the configured trigger wins and we flag the conflict to the
admin.
Activities. The activity type decides the suggestion type. An explicit agent or action
assignment always wins over anything read from the description; the description and
prompt shape the suggestion's content.

Suggestion vs autonomous action. A suggestion is shown to a person, who applies or
dismisses it; nothing happens until they apply it. An autonomous action is carried out
without a person approving it.
Autonomy setting, per activity with a policy-level default: always needs approval; may
act autonomously; or needs approval when confidence or context is below a threshold.
December: every action is a suggestion a person approves. An autonomous use case
starts only when both teams approve it, with a confidence threshold, an audit record
of every action, a way to undo it, and an off switch per tenant.
Topic 6: How do stage changes work?
Question: How are stage transitions represented, and can moving to the next stage itself
be a suggestion, for example prompting a PM or seller to advance once the required
activities are complete?
Answer: A project admin moves the stage; we only suggest the move, with
project.methodology.change_stage and evidence, sent to the project owner and
admins. Applying it runs the same step a person uses.
We'll build the stage-advance suggestion once it's approved. It's sent when the
evidence shows the stage's required activities are done, citing that evidence. A stage
can also look complete from a call (for example, scope signed off).
Knowing an activity is done: MOON-2389 defers activity tracking to a later phase. For
December we count an activity as done when a suggestion for it was applied and its
action succeeded (topic 3's outcome events). Activities done outside Veda won't be
seen until activity tracking exists.
Stage-change events say whether a person or an applied suggestion made the move,
with the suggestion_id . When one arrives, we suggest the next stage's activities.
The methodology stage and the Certinia stage stay separate, with no automatic sync.

Technical details: authentication and tracing
Question: How does the orchestrator authenticate to Veda? The meeting agreed Veda
implements scoped service credentials in its key management (KMS), with rotation and
secure storage, and provides a secure API so we retrieve credentials or authorization at
runtime rather than from static configuration.
Answer: We agree. What we need from the design:
1. Retrieval at runtime: our service calls Veda's credentials API and receives a short-
lived, scoped token (minutes, not days). No long-lived secret sits in our configuration.
2. The first call: that call needs an identity of its own. We propose our service's cloud
workload identity (for example, an AWS IAM role, per environment) rather than a
stored bootstrap secret. Veda confirms which identity it trusts.
3. Scopes: read the event feed, read context and methodology, write suggestions; each
limited to the tenants we're allowed to see. Nothing else.
4. Rotation and expiry: keys rotate in Veda's KMS without action on our side; tokens
expire and we fetch new ones before they do.
5. Revocation and incidents: either side can revoke our identity at once. We agree who is
called, and how fast, if a credential may be exposed.
6. Validation: a test in the dev tenant shows every call we make (feed, context,
methodology, catalog, suggestions) succeeds with the right scope and fails without it.
7. Tracing: we send X-Request-Id on every call and log it as our correlation ID.
This must be in place before any access is granted.
