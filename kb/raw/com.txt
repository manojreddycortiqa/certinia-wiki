MOON-2389 Client Operating Model —
Backend Architecture
Overview
A short, non-technical summary of MOON-2389. The other tabs hold the engineering detail.
The idea in one paragraph
Every client runs projects their own way: their own steps, their own rules, their own people in specific
roles. Today Veda gives everyone the same generic guidance. With this feature a client describes how
they work once, in Veda, and from then on the AI suggests the right next step to the right person at the
right moment, following that client's way of working instead of a generic one.

2. A project admin picks the methodology for the project in Project Settings (Figma) and gives team

3. As the project moves along (a call happens, a deadline nears, project health turns red), the AI
team's orchestrator reads the methodology and policies and decides what should happen next.

Domain model
The model adds 16 tables to the shared Supabase Postgres, plus one suggestions column, one users
column and a UNIQUE (tenant, form_id) constraint on query_form. Migrations live in
integration-sync-service/migrations/sprint-NN/.

entity diagram · library, roles and project runtime
Dashed lines are join tables. Stage to Policy goes through client_methodology_stage_policies, and
Activity to Role goes through client_activity_roles. Not drawn: audiences, audience_members and

Conventions for every table
• id uuid PK default gen_random_uuid().
• tenant bigint NOT NULL REFERENCES subscriber(tenant).
• Audit columns created_at, created_by, updated_at, updated_by. Append-only tables only
have the first two.
• RLS: enabled on every table, with a RESTRICTIVE tenant_isolation policy and no permissive
policy. The tables are reachable only through ISS, which uses the service role, as
ticketing_ticket_events already is.
• RPCs: SECURITY INVOKER, followed by REVOKE ALL ON FUNCTION … FROM PUBLIC, anon,
authenticated and GRANT EXECUTE … TO service_role. Existing migrations already revoke
from PUBLIC. A browser JWT therefore cannot call /rpc/publish_client_methodology with a
forged actor.
• Triggers fire on browser writes to project and project_assignment, so their functions run as
SECURITY DEFINER, owned by postgres, with a fixed search_path. Without that, an insert into
an RLS-protected table would fail and break today's owner and team saves.
• Unique names use name_key text GENERATED ALWAYS AS (lower(btrim(name))) STORED.
• Ordered children use a position int that runs 1..N, checked by
require_contiguous_positions (src/shared/utils/positioning.py). The UNIQUE
constraint is DEFERRABLE INITIALLY DEFERRED, so a reorder can run inside one RPC.

Trigger parameters. The type and reason stay real columns, because the orchestrator and the policy list
filter on them and the CHECKs depend on them. Anything a reason needs beyond its name, such as a
threshold, a metric or a time window, goes in trigger_params. Each (type, reason) pair in the ISS
catalog declares a Pydantic model for its parameters; a pair without parameters accepts only {}. ISS
validates on create and update, and GET /operating-model/catalog returns each model as a JSON
Schema, so the Create Policy form can render the fields without a frontend release per reason. Each
policy revision stores the parameters with the rest of the policy, and a published version references the
revision it was built from, so the parameters are pinned like everything else.
Catalog changes are additive: a new reason or a new optional parameter needs nothing else. Renaming
or removing a key, or making a parameter required, needs a data migration and the AI team's
agreement. We store and serve the parameters; the orchestrator decides when the condition is met.
Not now: several triggers per policy, or AND/OR conditions. Figma shows a single trigger and no story
asks for combinations. If that changes, the three columns move one-to-one into a
client_policy_triggers child table.

Rules
• Save (PUT …/structure) works in any status except archived. It bumps revision, which is only
a concurrency counter (the snapshots are versions), and never touches versions.
o Ids come from the client. In the structure RPC, an id already in this draft is updated and
an unknown id is inserted with that value. An id that belongs to another methodology or
tenant fails with 422 operating_model.methodology.invalid_id, which reveals
nothing about the owner. There are no temporary keys and no id mapping.
• Publish creates version N+1, sets current_version_id and moves draft to active.
o It is idempotent: if the new snapshot hash equals the current version's hash, it returns
the existing version.
• Archive is allowed while projects are pinned. Restore returns the methodology to its previous
status.
• Delete is allowed only while the methodology has never been published; the RESTRICT FK from
versions enforces it. Otherwise the API returns 409 operating_model.methodology.in_use
and the UI offers Archive.
• has_unpublished_changes is true when revision moved since the last publish, or when any
attached policy's live revision is newer than the revision in the snapshot.

Policy revisions
• Every policy save (fields or activities) bumps client_policies.revision and appends a row to
client_policy_revisions inside the same RPC.

• Publishing is blocked while a stage references an archived policy

Methodology tree format
A stage holds one ordered list, items. Every item has id and kind; the other fields depend on kind.
Reads and writes use the same envelope, so a new kind later (a checklist, a milestone, a nested policy) is
one new variant with no change to stages or to existing kinds. Today there are two kinds, activity and
policy.
Write shape, used by PUT …/structure and by policy create and update:
type StageItemInput = ActivityItemInput | PolicyItemInput
type ActivityItemInput = {
kind: "activity"
id: string // client-generated UUID, permanent
name: string
type: string // activity type catalog key
description?: string
role_ids: string[]
agent_id?: string
prompt?: string
is_required: boolean
}
type PolicyItemInput = {
kind: "policy"
id: string // client-generated UUID of the stage-policy link
policy_id: string // the shared policy; its content is not edited here
}

• Ordering and cursor: the feed is ordered by (txid, seq) and only returns rows whose txid <

o Every transaction below that horizon has finished, so no row can appear later behind the
cursor, however long a transaction runs.
o The cursor is the last (txid, seq), encoded as an opaque string.

unless that is decided otherwise.

Stage-advance check
1. Moving backward, or staying on the same stage, is always allowed.
2. Moving forward: the RPC collects required activities in every stage the move passes (from the
current stage up to, not including, the target) whose state is not completed, skipped or not
applicable.
3. If that list is not empty, PUT …/methodology/stage returns 409
operating_model.project_methodology.required_activities_incomplete with
meta.activities[] (stage name, activity name, activity id).
4. The frontend opens the Method Deviation modal once per listed activity. Each Confirm sends
POST …/methodology/deviations, which also marks the activity skipped.
5. The frontend retries the stage change, which now succeeds.
When autonomy is on and the orchestrator moves the stage directly, the move is allowed and the
missing required activities count as overdue; only a person can write a deviation reason.
Adherence
The Project IQ frame in Figma shows "Medium adherence" next to the stage. In the first version that
label stays hidden.
• Due = required activities in stages before the current stage, counted per (stage, activity).
• Done = due activities that are completed. Justified = due activities skipped with a deviation.
• Score = (done + justified) / due × 100. With no due activities there is no score.
• Level: High at 85 or above, Medium from 60 to 84, Low below 60 (placeholder thresholds for
Product to confirm).
• Deviations count as justified but are reported separately, so a project that skips everything with
reasons is still visible.
• get_project_methodology_adherence(p_project) computes it from the pinned snapshot
and the state rows. Every RPC that changes the stage, an activity state or a deviation recomputes
it and stores adherence_score numeric(5,2) and adherence_level on
project_methodology. A level change writes
project.methodology.adherence_level_changed ({from_level, to_level, score}).
• A daily workflow-service beat job calls snapshot_project_methodology_adherence() to fill
project_methodology_adherence_snapshots (project, snapshot_date, version_id,
stage_id, required_due, required_done, required_justified, score, level; PK (project,
snapshot_date)).
• API: GET /projects/{project_id}/methodology/adherence (ViewerProjectSummary)
returns the current score and the daily trend; the methodology summary gains adherence
{score, level}. The stage card shows a dot with the level and the score in a tooltip.

AI-proposed changes to methodologies and policies
The epic requires that "AI-derived methodology or policy refinements must be proposed for client
approval before becoming active" (base.md:136, :178).
• Producers: document extraction (after the uploaded event), the "Engage with Agent" chat in the
editor, and later refinements learned from transcripts.
• Table operating_model_proposals: entity_type (methodology / policy), entity_id nullable
(null when a new policy is proposed), base_revision int, proposed jsonb, summary text,
source (operating_model.document / agent.chat / callpilot.call), source_ref jsonb, status
(pending / accepted / rejected / superseded), created_by_service, decided_at, decided_by,
decision_note.
• Shape: proposed uses the same body as PUT …/structure for a methodology, or PUT
/client-policies/{id} for a policy. base_revision records the revision the AI read.
• API: internal POST /internal/orchestration/proposals (proposals:write, {entity_type,
entity_id?, base_revision, proposed, summary, source, source_ref}); public GET
/client-methodologies/{id}/proposals and POST
/operating-model-proposals/{proposal_id}/accept and /reject (RequireTenantAdmin).
• Review: the editor shows a banner "AI proposed changes" and draws the diff on the canvas, with
Accept and Reject.
• Accept: RPC accept_operating_model_proposal applies the proposal through the structure
RPC. If base_revision is older than the methodology, it returns 409
operating_model.proposal.stale; the user asks the agent again or chooses "Replace draft".
Document extraction is slow, so its proposals are often stale.
• Activation: accepting a methodology proposal changes only the draft, and Publish stays a
separate human step. Policies have no draft, so accepting a policy proposal writes a new
revision; the acceptance is the approval.
• Superseding: a new pending proposal for the same entity supersedes older pending ones.
• Events: operating_model.proposal created, accepted, rejected, superseded.
• AI triggers: once proposals exist, the orchestrator can suggest a trigger for a policy that has none
by posting a policy proposal.
